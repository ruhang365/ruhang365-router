# 入行与成长发现合同

## 从用户表达确定当前需要

探索转行、在岗成长、跨境入行可以从日常表达开始；具体问题也可以直接进入帮助。条件摘要只保留与这轮建议有关的事实：相关经验、想解决的问题或想了解的方向、可用时间／预算／材料，以及明确不想做的事。未说明的条件就是未知；工作年限不能转换为 AI 能力等级，也不能凭“不会代码”推断用户永远不愿学习。

只问会改变推荐、参与门槛或第一步的问题。用户想比较方向时，先解释差异即可；要做长期计划而没有时间预算时，再问可投入时间。目标与条件冲突时具体说明哪里冲突，给一个有理由的取舍问题；不能默默改目标或承诺靠工具消除限制。已有具体任务不用重新欢迎、诊断或走完题目。

## 用同一目录找候选

--guide career-change|work-growth|cross-border --answer question_id=option_value 在本地计算。条件按键 AND、选项 OR；unknown/skip 不作为正向依据。足以推荐就结束追问。引用资料须存在且当前有效；不足时说明覆盖缺口，不以“同为初学者”补入无关资料。

先读取当前目录实际问题和选项，再把含义明确的表达映射为答案。用户只说“想了解 AI 产品”，不代表已决定换岗，不能填入 `route=new-role` 作为用户事实；先用主题检索比较新分工与原岗升级，确实影响下一步时再追问。修改目标后重新生成有效答案，移除旧分支条件；用户的其他事实和排除项仍保留在会话。

检索输入使用正向主题与期望用途，不把整段自述原样送进关键词检索。例如“产品经理，五年经验，每周四小时，不会代码，想了解 AI 产品”可检索“AI 产品 岗位职责 模型评估”，其余条件用于解释和安排；“不做自媒体”保留为排除项，不能作为寻找自媒体方法的正向词。不要为了凑够选项扩大到无关方向。

`--identity`、`--goal`、`--experience`、`--constraint`、`--deliverable` 是现有本地检索参数。职业经验与新领域经验分别理解；只传已明确的条件。`--constraint` 仅能匹配目录已有标签，不保证脚本理解自由文本中的时间、否定或矛盾。宿主仍需逐项核对用户条件与资料的 applicability、access、governance、guidance、完成标准和实际内容。无需为自由表达新增模型接口、个人画像库或第二份知识目录。

引导另支持 `--condition key=value`，与 Web 条件严格同值：`experience=new|product|operations|technical|business`；`coding=none|basic|ready`；`weeklyHours=2|4|8`；`budget=0|1000|more`；`supplyChain=yes|no|unknown`。空值或未传表示未说明；`experience` 的普通任务参数不等于这里的经验选项。同一条件只能传一次，修改时替换旧值，非法或冲突输入会报错，不能默默覆盖。条件仅本地解释，不发给公开 API；预算为 0 时同步应用目录的 `free-only` 排除标签，不推断所有余下内容都无费用。

`conditionNotes` 按资料 ID 给出与 Web 相同的经验迁移、代码门槛、时间和费用缺口说明。在岗引导优先已有推荐中的原岗升级，不凭未说的经历补填条件。比较推荐包含多个 `resourceIds` 时，先同等比较这些方向；只有用户条件和资料确实支持取舍时才给有边界的优先建议。当前目录未提供比较选项时，可按实际返回 ID 分别读取，不能假造选项或声称三个岗位都已命中。

`relatedLinks` 保留方向中明确列出的资料链接；`communityMatches` 中 `linked_id` 来自所选方向的显式关联及其工作流节点模板，`query_coverage` 来自用户主动查询的严格主题覆盖。答案 value/label 不再拼成宽泛搜索词，避免“产品”误配视觉资料、“运营”误配小店获客。普通任务的 `--query` 路由保持兼容。读取 career 的 `structured.workflow_ids` 与 `related` 可找到方法；再按该 workflow ID 读取节点模板。只有目录实际返回的内容才是可用材料，不生成或下载未经授权的关联正文。

例如明确要整理小店顾客反馈时，可用：

```bash
python3 "$SKILL_DIR/scripts/route_ruhang365.py" \
  --query "顾客反馈 整理 改进清单" --intent knowledge \
  --goal customer-insight --deliverable customer-feedback-review \
  --catalog "$SKILL_DIR/catalog/community-full-1.1.0.json" --format json
```

参数只是候选线索，不是已经完成任务。按实际返回的稳定 ID 读取所选资料，不根据标题猜造 ID，每轮最多五项。若返回 `detail=null`，先核对当前目录 ID，不把这次读取当成已看过内容，也不据此宣称整个主题没有资料。`resources[].guidance` 提供获准公开的职业职责、入行路径或平台条件；`detail.structured` 提供目录已有 Workflow／Prompt 内容；只有实际返回 `body` 才能说读取了额外正文。线上正文失败时保留已核验的目录结构，并说明缺失部分；离线与受限内容按现有读取边界处理。

## 从内容形成建议

关键词候选与固定 guidance recommendation 均是依据，不是个人适配结论。先核对主题、所需材料、参与条件和用户排除项，再决定是否采用。只有“AI”“新手”或“产品”词面相同的条目不能决定路线；无适用资料时最多换一组更明确的任务词，仍缺内容就说明，并可提供标明为通用 AI 建议的帮助。

实际案例只有在资料确实包含可追溯经历或结果时才称为案例。比较与用户相似的职责、条件、市场和资源，并说明差异；教程可支持方法，不能包装成“某位同背景的人成功转行”。招聘、讨论和成交是不同信号，引用保留来源、日期、地区与未核实项。推荐表示“值得先了解”，不保证就业、收益、资格或个人胜任。

探索：给一个有条件依据的优先了解起点；必要时对照最多两个方向，说清各自的门槛和取舍。只想看懂差异时，解释与比较就能完成帮助，不附强制练习或长期计划。

具体问题：给当前一步、所需材料、可观察完成标准和卡住后的调整。没有实际材料时交付可填写模板或脱敏输入要求，不编造分析结果。用户已完整委托时完成约定产出，而不是停在“你可以这样做”。

持续学习：按用户实际投入安排第一周，将阅读、操作与复核都计入；可以用时间区间并说明这是估计。完整方法超出时间时标明本周只做到哪部分。之后依据完成、卡住或条件变化调整，不默认固定十二周、每天一小时或考试／作品回传。

## 继续、修改与续接

“完成”用用户描述的实际状态解释，不变成能力认证；“卡住”先定位卡在哪一步，调整一件影响下一步的事；“条件变化”重新看冲突和资源适用性；“换方向”保留可迁移条件，撤掉旧路径的承诺。

跨会话需要时直接给可复制的简短 Markdown：目标与当前需要、相关条件及明确排除项、已做／卡住、资源 ID 和链接、下一步、未知与待核实项。由用户保存并带入下一会话；不自动写长期记忆，也不将这份摘要当作跨设备同步或后台提醒。

内容来自 Supabase 受控发布；Web 与 Skill 消费同一版本。候选与快照是分发产物，不能反向成为第二可编辑主源。未发布候选明确标为本地体验。

旧 --query 场景接口保留，供明确需要使用。覆盖以实际目录为准，不在 Skill 中维护另一份假定永远最新的方向列表。
